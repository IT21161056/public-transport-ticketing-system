# GEMENI – User Registration & Transport Access Design Decisions

## 1. Purpose

This document defines the frontend and user-flow decisions for user registration, guest access, transport-token purchase, and QR-code acquisition.

The main goal is to keep the experience simple and fast while collecting only the minimum information required by the transport system.

---

## 2. Core Design Principles

### Minimal personal data

The system should not maintain unnecessary personal information about users.

For a normal/local user, the minimum profile information is:

- Full name
- Phone number

No unnecessary profile fields should be requested during registration.

### Two access types

The system should clearly separate two types of users:

1. **Registered Local User** – a user with a persistent account, account credits/wallet balance, and a persistent QR credential linked to that account.
2. **Guest User** – a temporary visitor who does not need a permanent account and receives a temporary paid transport token/QR with an explicit expiration time.

These are intentionally different models. A local user should **not** receive a temporary guest token. A guest should **not** need a permanent local-user profile.

### Fast access

A user should be able to move from the website to a valid transport QR code with as few steps as possible.

### QR as the access credential

Both user types can use a QR code, but the QR has a different meaning:

- **Local user QR:** persistent/account-linked credential used repeatedly while the account is active.
- **Guest QR:** temporary credential linked to a guest transport token and valid only until its expiration time.

---

# 3. Entry Point

When a user opens the transport provider website, the system should provide a simple landing page explaining that the user can either create a permanent account or obtain temporary guest transport access.

Recommended primary actions:

- **Create account**
- **Continue as guest**

The UI should make the difference between the two options obvious before the user starts the process.

---

# 4. Registered Local User Flow

## 4.1 Registration purpose

A local user creates an account because they may need to return to the service, manage their access, view active transport permissions, or use the account again in the future.

The account should therefore contain a small persistent profile.

## 4.2 Registration fields

The initial registration form should request only:

### Required

- **Full name**
- **Phone number**

### Not required during initial registration

Avoid requesting:

- Address
- Date of birth
- Gender
- NIC/passport number
- Profile photo
- Email address
- Unnecessary demographic information

These should not be introduced unless a future transport/business requirement specifically needs them.

---

# 5. Phone Verification

## 5.1 Preferred verification method

Use **OTP-based phone verification** rather than email verification.

The phone number is the primary identity/contact information collected by the system, so verifying ownership of the phone number is more consistent with the minimal-data design.

## 5.2 OTP flow

Recommended flow:

```text
Enter Full Name + Phone Number
              ↓
        Request OTP
              ↓
      OTP sent to phone
              ↓
         Enter OTP
              ↓
       Verify phone
              ↓
      Create user account
              ↓
       Open user profile
```

## 5.3 OTP UX requirements

The OTP screen should include:

- Phone number being verified, preferably partially masked
- Numeric OTP input
- Countdown/resend timer
- **Resend OTP** action after the cooldown period
- Clear error message for invalid OTP
- Clear handling for expired OTP
- Ability to change the phone number and retry

The frontend should never expose or display the actual OTP value received by the backend/SMS provider.

---

# 6. Account Creation Result

After successful OTP verification:

1. The backend creates the user account.
2. A unique internal user ID is generated by the system.
3. The user is authenticated.
4. The user is redirected to the profile/account area.

The user should not need to manually create a username or system ID.

Example conceptual identity:

```text
User
 ├── Internal User ID (system generated)
 ├── Full Name
 └── Verified Phone Number
```

---

# 7. Registered Local User Account, Credits and QR

## 7.1 Persistent account model

A registered local user has a persistent account. They do not need to create a new temporary transport token for each visit or trip.

Conceptually:

```text
Local User
 ├── User ID
 ├── Full Name
 ├── Verified Phone Number
 ├── Account Credit Balance
 └── Persistent QR Credential
```

The backend is the source of truth for the account, balance, and QR credential.

## 7.2 Account top-up

Local users can add money/credits to their account through a top-up flow.

```text
Login / Open Account
        ↓
View Credit Balance
        ↓
Select Top-up Amount
        ↓
Payment
        ↓
Top-up Confirmed
        ↓
Account Balance Updated
```

The frontend displays the balance returned by the backend. It must not calculate or trust the balance as the authoritative value.

## 7.3 Persistent local-user QR

After registration, the system can provide the local user with a persistent QR credential linked to their account. The same QR can be presented repeatedly.

The local-user QR is **not an expiring guest token**. Its validity depends on the registered account and the transport business rules.

Example:

```text
My Transport QR

       [ QR CODE ]

Account: Active
Credit: 1,250.00

[ Top up credits ]
```

The QR should contain only a secure credential/reference and should not expose unnecessary personal data.

## 7.4 Local-user scan/tap validation

When a local user presents the QR, the transport system should check the account/credential on the backend. Depending on the transport business rules, the system can then authorize the ride and deduct the required amount from the account balance.

Conceptually:

```text
Scan Local User QR
        ↓
Find account/credential
        ↓
Account valid?
   ├── No → Reject
   │
   └── Yes
        ↓
Sufficient credits?
   ├── No → Reject / Top-up required
   │
   └── Yes
        ↓
Authorize transport access
        ↓
Deduct applicable credits
        ↓
Record transaction
```

The exact fare-deduction rule belongs to the backend/business logic.

# 8. Guest User Flow

## 8.1 Purpose

Guest access is intended for temporary visitors who do not need a permanent account or profile.

The guest should be able to obtain transport access without completing the full registered-user process.

## 8.2 Guest identity

The system should automatically create a temporary guest identity.

Conceptually:

```text
Guest Session
 ├── Guest ID (system generated)
 ├── Device/Session Identifier
 ├── Selected access period
 ├── Payment status
 └── Transport token / QR
```

The guest should not be required to manually create an account ID.

---

# 9. Device Identification Consideration

The initial concept uses a device identification code to associate the temporary guest session with a device.

For the frontend architecture, this should be treated as a **device/session identifier**, not as a permanent personal identity.

Recommended behavior:

- Generate an anonymous client identifier when the guest flow starts.
- Store it locally on the device/browser.
- Associate the identifier with the temporary guest session on the backend.
- Do not treat the identifier as a substitute for authentication.
- The backend-generated guest ID remains the authoritative identifier.

A browser/device identifier can be lost when browser storage is cleared, the user changes devices, or privacy settings restrict storage. Therefore, the QR/token itself and backend record must remain authoritative.

---

# 10. Guest Access Period Selection

The guest must select how long transport access is required before payment.

Recommended initial periods:

| Option | Duration |
|---|---:|
| 1 Day | 24 hours |
| 2 Days | 48 hours |
| 3 Days | 72 hours |
| 7 Days | 1 week |

These options keep the selection simple while covering common short-term visitor requirements.

The actual duration rules should be defined by the backend/business rules. The frontend should display the available options returned by the backend rather than hard-coding pricing or availability rules when practical.

---

# 12. Pricing Display

After selecting a period, the system should clearly show the amount that must be paid.

Example:

```text
Transport Access

1 Day       $X
2 Days      $Y
3 Days      $Z
7 Days      $W
```

After the user selects a duration:

```text
Selected Access
3 Days

Amount to pay
$XX.XX

[ Continue to payment ]
```

The final amount should be calculated/validated by the backend. The frontend should display the amount returned by the backend and should not be considered the source of truth for pricing.

---

# 13. Payment Flow

The payment page should be intentionally simple.

Recommended sequence:

```text
Access Period
     ↓
Order Summary
     ↓
Payment Method
     ↓
Payment Processing
     ↓
Payment Result
```

The UI must support at least these states:

### Payment pending

The system is waiting for confirmation from the payment provider.

### Payment successful

The purchase is confirmed and the transport token can be issued.

### Payment failed

The user can retry or return to the payment method selection.

### Payment cancelled

The user can return to the purchase summary without receiving a valid transport token.

---

# 14. Transport Token

For the guest flow, after successful payment, the backend should generate a unique temporary transport access token. A registered local user does not use this temporary-token flow; their persistent QR is linked directly to their account credential.

Conceptually:

```text
Guest
   ↓
Successful Payment
   ↓
Temporary Transport Access Token
   ↓
Guest QR Code
```

The transport token should be unique and validated by the backend when scanned.

The frontend should not generate the authoritative access token itself.

---

# 15. QR Code

## 14.1 QR generation

After successful payment, show a dedicated QR-result screen.

The screen should contain:

- QR code
- Access type
- Validity period
- Expiration date/time
- Basic transport-access status
- Option to save/download the QR

Example:

```text
Transport Access

        [ QR CODE ]

Guest Access
Valid for: 3 Days
Expires: 2026-10-03 18:30

Status: Active

[ Save QR ]
```

## 14.2 Screenshot support

The design should allow users to take a screenshot as a practical backup.

The QR screen should therefore contain all critical information directly on the screen without requiring an additional navigation step.

However, screenshots should not be treated as the authoritative source of validity. The backend should validate the token when the QR is scanned.

---

# 16. Guest Token Validation and Scan/Tap State

The backend must be able to determine whether a guest QR is still valid at the exact time it is scanned/tapped. The QR image itself is not the source of truth.

For every guest transport token, maintain at least:

```text
GuestTransportToken
 ├── tokenId
 ├── guestId
 ├── issuedAt
 ├── startsAt
 ├── expiresAt
 ├── status
 ├── lastScannedAt
 └── scanCount / scan history
```

Recommended states:

```text
PENDING_PAYMENT
      ↓
ACTIVE
  ↙       ↘
EXPIRED   REVOKED
```

A scan/tap should perform a backend validation similar to:

```text
Guest QR scanned
       ↓
Find token
       ↓
Token exists and is active?
   ├── No → Reject
   │
   └── Yes
        ↓
Current time < expiresAt?
   ├── No → Mark/return EXPIRED
   │
   └── Yes
        ↓
Accept access
        ↓
Record scan/tap time and validation event
```

For a period-based visitor pass such as 1, 2, 3, or 7 days, the token should normally remain usable throughout its validity period. Therefore, a successful scan should **not automatically invalidate the token** unless the business rule explicitly defines the guest token as single-use.

If the product later introduces single-use visitor tickets, the backend can instead set:

```text
ACTIVE → USED
```

after the first successful scan and reject subsequent scans.

This distinction must be implemented in the backend rather than inferred from the QR image.

# 17. QR Security Considerations

The QR should contain a secure reference/token rather than unnecessary personal information.

Avoid encoding sensitive information directly into the QR, such as:

- Full personal profile data
- Phone number in plain text
- Payment card information
- Passwords
- Internal security secrets

A preferred conceptual structure is:

```text
QR
 └── Secure Transport Token / Token Reference
```

The transport verification system can use that token to query the backend and determine whether the access is valid.

---

# 18. Registered User vs Guest

| Feature | Registered Local User | Guest / Visitor |
|---|---|---|
| Full name | Yes | No account profile required |
| Phone verification | Yes, OTP | Not required for guest flow |
| Permanent profile | Yes | No |
| Internal identity | Permanent user ID | Temporary guest ID |
| Device/session ID | Optional | Recommended for temporary session continuity |
| Temporary transport token | **No** | **Yes** |
| Account credit balance | Yes | No |
| Top-up credits | Yes | Not applicable |
| Persistent QR credential | Yes | No |
| Guest access period selection | Not required for normal account use | Yes |
| One-time purchase for access period | No; top up account credits instead | Yes |
| QR reuse | Yes, while account is valid | Yes, during token validity window |
| QR expiration | Based on account/credential status | Explicit `expiresAt` |
| Long-term profile management | Yes | No |

The key distinction is **persistent account + reusable QR + credits for local users** versus **temporary session + paid expiring token for guests**.

# 21. Session and State Management

The frontend should maintain enough state to move users through the correct flow without mixing local-account and guest concepts.

### Local user state

```text
Authenticated Account
    ↓
Credit Balance
    ↓
Persistent QR
    ↓
Scan / Transport Transaction
```

### Guest state

```text
Guest Session
    ↓
Selected Duration
    ↓
Order/Checkout ID
    ↓
Payment Status
    ↓
Issued Temporary Token
    ↓
Temporary QR
```

The backend remains the source of truth for:

- User identity
- Guest identity
- Account credit balance
- Access validity
- Pricing
- Payment state
- Token state
- QR credential state
- Guest expiration
- Scan/tap history

The frontend should only display and interact with this backend state.

---

# 22. Important Error States

The frontend must handle failures explicitly instead of assuming every step succeeds.

Required cases include:

### Registration errors

- Invalid phone number
- Missing name
- Phone number already registered
- Server error

### OTP errors

- Incorrect OTP
- Expired OTP
- Too many attempts
- OTP delivery failure

### Guest errors

- Unable to create guest session
- Invalid duration
- Session expired

### Payment errors

- Payment declined
- Payment cancelled
- Payment timeout
- Payment provider unavailable
- Payment succeeded but frontend did not receive confirmation

### QR errors

- Token generation failed
- QR generation failed
- Access expired
- Access revoked
- Token not found

Every failure state should provide a clear recovery action where possible.

# 24. Guest Session Expiration

Guest accounts should be temporary by design.

A guest session should have an explicit lifecycle:

```text
Created
  ↓
Pending Purchase
  ↓
Paid
  ↓
Active
  ↓
Expired
```

Expired guest sessions should no longer grant transport access.

The backend should define when temporary guest records are archived or deleted according to the system's retention requirements.

---

# 25. QR Verification Model

The QR is an access credential, but its validation model depends on the user type.

## 23.1 Local registered user QR

The local user's QR is a persistent credential linked to their registered account. It can be reused for multiple transport accesses.

```text
Local User
    ↓
Persistent Account
    ↓
Persistent QR Credential
    ↓
Scan / Tap
    ↓
Backend
    ↓
Validate account + QR + credit balance
    ↓
Authorize access / apply credit transaction
```

A local user's QR should not become an expired guest token after one scan. The account and credit balance determine whether the credential can be used.

## 23.2 Guest QR

The guest QR represents a temporary paid transport token. Its validity is explicitly time-bound.

```text
Guest Session
    ↓
Paid Guest Transport Token
    ↓
Temporary QR
    ↓
Scan / Tap
    ↓
Backend
    ↓
Validate token status + current time vs expiresAt
    ↓
Accept / Reject
    ↓
Record scan/tap event
```

For a time-based guest pass, multiple scans may be permitted until `expiresAt`. If the business later introduces a single-use guest ticket, the token lifecycle can instead use `ACTIVE → USED` after the first successful scan.

The QR image itself must never be treated as proof that the access is valid. The backend must make the final validation decision.

# 26. Frontend Design Goals

The registration and guest-purchase UI should feel like a utility service rather than a traditional social application.

Priorities:

1. **Minimal input**
2. **Clear choices**
3. **Few screens**
4. **Obvious progress**
5. **Strong payment confirmation**
6. **Immediate QR access**
7. **Readable QR result screen**
8. **Useful error recovery**

Avoid unnecessary animations, forms, profile customization, or onboarding steps.

# 28. Final Design Decision

The frontend will use a **minimal-registration + persistent-local-account + temporary-guest-access model**.

Registered local users are identified primarily through a verified phone number and full name. Phone OTP is the preferred verification mechanism. A local user receives a persistent account and a persistent QR credential linked to that account. They can top up account credits and reuse the same QR while the account remains valid.

Guests do not need a permanent profile. The system creates a temporary guest identity/session. The guest selects a predefined transport-access duration, pays the displayed amount, and receives a backend-issued temporary transport token represented as a QR code. The guest token has an explicit `startsAt`/`expiresAt` validity window and scan/tap history.

The architecture should keep the distinction clear:

```text
REGISTERED LOCAL USER
Persistent account + credits + persistent QR
            │
            └── Reusable while account is valid

GUEST / VISITOR
Temporary session + paid temporary token + QR
            │
            └── Valid only within expiresAt window

Both
   ↓
Backend QR validation
   ↓
Transport access decision
```
